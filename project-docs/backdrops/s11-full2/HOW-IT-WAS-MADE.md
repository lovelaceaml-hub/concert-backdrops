## 1. The engine: what makes a picture

### In plain words
Nothing in these videos is filmed, painted or generated by an AI image model. A Python program calculates every picture, 30 or 60 times for each second of video.

Think of it as a virtual film set:
- A 3D world measured in metres: a sea of glass (a mirror lake), hills, a sky, Mount Zion, a stage, the Earth.
- A virtual camera that flies through it.
- Everything in that world (people, buildings, words, comets, clouds) is made of points of light: thousands to hundreds of thousands of tiny glowing dots, lines and ribbons.

The program "photographs" this set the way a real camera would:
- Bright lights glow and bleed into their surroundings (bloom).
- What is out of focus goes soft and turns into round blurs (depth of field).
- Distant things fade into haze (fog).
- Everything is reflected in the lake.
- Very bright light is rolled off gently, like film, instead of clipping (the filmic curve).

The finished pictures go to ffmpeg, a standard video tool, which turns them into an MP4.

Two properties matter for everything that follows:
1. **Every picture is a pure function of the song time.** Ask for the picture at 1:40.26 and you always get exactly the same picture, whether you render the whole film in order or just that one frame. That is what lets many computers each render a different piece and still have the pieces fit together perfectly.
2. **There is no graphics card.** The cloud computers that rendered this have only processors (CPUs). The program still uses OpenGL, the normal graphics language, but a software version of it (Mesa "llvmpipe") draws on the CPU. That works anywhere, but it is slow: a few seconds of computer time per picture at draft size. This is the single biggest limit on speed and quality.

### Technical detail

**The renderer** is `engine/render.py` (the "Renderer" class):
- It sets `LIBGL_ALWAYS_SOFTWARE=1` and opens `moderngl.create_standalone_context(backend="egl")`. In the cloud this reports `llvmpipe (LLVM 20.1.2, 256 bits)`: OpenGL and GLSL shaders executed on the CPU.
- One frame, in order:
  1. The song's `params(t)` gives colours, sun, exposure and fade for time t. The 3D layer's `adjust(t, P)` computes the camera and world for this frame.
  2. Sky pass into a half-float (16-bit) sky buffer.
  3. Light pass: everything that emits light is added (additive blending) into a half-float **HDR light buffer**, where values can go far above 1.0. The 3D layer's `draw()` adds every point set here, each with its mirror image in the lake.
  4. Bloom: four blurred copies at 1/2, 1/4, 1/8 and 1/16 size.
  5. Background: the 3D layer's sky dome, hills, lake, mist, light shafts and rays.
  6. Composite shader (`COMP_FS`): sky plus background plus light plus weighted bloom; vignette; exposure; the filmic curve `(x*(2.51x+0.03))/(x*(2.43x+0.59)+0.14)` (the widely used ACES fit); gamma 1/2.2; a saturation lift; a mild S-curve; fine film grain against banding.
  7. Read back 8-bit RGB and pipe it to `ffmpeg -c:v libx264 -crf ... -pix_fmt yuv420p` (bt709, faststart).

**The 3D layer** is `engine/p3d/` (switched on when a song defines `P3D`). Its contract is in `engine/p3d/api.py`:
- Units are metres, y is up, the lake is the plane y = 0, a person is about 1.7 m tall.
- Colours are linear light added to the HDR buffer. `lin("#hex")` turns a display colour into light; `show("#hex")` gives the light that will display as exactly that colour.
- Sizes are physical (metres), and a point keeps its energy whether it is sharp, blurred or streaked. So a scene looks the same in a quarter-size draft and at 4K.
- A **point set** is any object with `sample(t)` returning a batch: positions `pos (N,3)`, `size`, `color`, `alpha`, `kind`, plus optional `pos2` (for lines and ribbons), `emit` (extra brightness for glints), `normal`, `vel` (motion blur), `birth` (when each point appears), `seed` (twinkle), and per-batch settings such as `twinkle`, `rim`, `dof`, `fog`, `reflect`, `streak`, `fade`, `flash`, `pulse`, `paint`.
- Sprite **kinds**: soft, spark, disc, flake, petal, bird, line, ribbon (and a heart sprite).
- `engine/p3d/layer.py` draws them as instanced quads; `engine/p3d/shaders.py` gives each sprite a flat disc with a soft edge whose size is the lens's circle of confusion (zero on the focus plane), fades it with height-and-distance fog, and mirrors it in the lake with ripple smear.
- `engine/p3d/camera.py` gives the camera rig (orbit, dolly, crane, fly, hold, cuts, handheld drift, shake, rack focus). `engine/p3d/world.py` blends "looks" (night, dusk, dawn, sunrise, golden, day) setting by setting.

**People** (`engine/p3d/body.py`, `cloth.py`, `crowd.py`):
- Bodies come from the free MakeHuman base mesh (CC0) on a skeleton, moved by motion capture (CMU) and hand-posed gestures. Faces are never drawn.
- Garments are cloth simulated at fixed 1/120 s steps, so any frame gives the same answer in any order.
- Crowds bake a few prototype bodies once per kind (stand, walk, raise, kneel, open...) and then place hundreds of instances, each turned, mirrored and shifted in time. The bakes are cached on disk (`P3D_CACHE`) so a machine only pays for them once.

**Known limits** (from `engine/UPGRADE-HOWTO.md`, section V): points are light and cannot hide each other (solid bodies come from a separate dark "mask" pass); hills, clouds and lake are formulas, so there are no cast shadows; motion blur is a stretch along the path; drawing costs about 0.5 s of CPU per million points, doubled by the mirror.

## 2. Listening to the song

### In plain words
Before any picture was designed, the recording was measured, because Anthony's first instruction was: "First, I want you to review the song. Find all the music notes so that we can match the design to the song, so the intensity matches the song."

The song runs 260 seconds; the film adds a 15 second calm hold after the last chord, so it is 275 seconds (4:35) long. The measurements found:
- Key F major, about 103.4 beats per minute (about 99 in the intro, about 111 in the coda), 112 bars.
- Three big "slams" where the full band and low end crash back in after a build: 1:22.08, 2:42.86 and 3:21.73. These became the film's three biggest moments.
- A step down at 4:00.19, a held breath at 4:07.5 to 4:09.5, and the last chord at 4:14.07.

From these, the film was divided into seven sections, which later became the seven render machines' jobs:

| Section | Time |
|---|---|
| Intro | 0:00 to 0:40 |
| Verse 1 | 0:40 to 1:22.08 |
| Chorus 1 | 1:22.08 to 2:01.32 |
| Verse 2 | 2:01.32 to 2:40 |
| Chorus 2 | 2:40 to 3:21.73 |
| Coda | 3:21.73 to 3:58.8 |
| Ending | 3:58.8 to 4:35 |

Then the computer measured, sixty times a second, how much of each sound there is: the bass, the kick drum, timpani hits, strings, brass, the choir, high voices (sopranos and altos) and low voices (tenors and basses). Those measurements are curves from 0 to 1, and almost every effect in the film reads one of them. That is how a flash lands on a timpani hit, or the sea glitters with the bass.

The most important moments were also timed by hand (the slams, the 26 "hits", the key moments), because automatic beat tracking was a little off on some of them (see problem 21 and finding f42).

### Technical detail
- `tools/s11_full2/s11_prepare.py`:
  - restores the pinned engine;
  - checks the recording's SHA-256;
  - writes `work/s11_full2/score.wav` (trimmed at 260.0 s, padded to 275 s, 48 kHz 24-bit);
  - runs the pinned `engine/analyze.py` to write `features.npz`. That uses librosa at 22,050 Hz with hop 512 (about 43 values a second): `rms` loudness, band energies (low 20 to 200 Hz, mid, high, air), spectral centroid, onset strength, beat times `beat_t` and tempo, and a harmonic/percussive split.
- `tools/s11_full2/s11_music_map.py` (written in round 6) writes `music_fx.npz` with librosa at 24 kHz and hop 400, exactly 60 values a second:
  - `bass` (30 to 150 Hz) and `bass_rel`;
  - `kick` (with times `kick_t`), `timp` (low percussive onsets still ringing 0.2 s later, with times `timp_t`);
  - `strings` (harmonic 200 to 2000 Hz) and `swell` (how fast it rises);
  - `brass` (bright harmonic 1 to 4.5 kHz) with `brass_hit`;
  - `choir` (voiced probability from `librosa.pyin` times the vocal band);
  - `high` (voiced 500 to 2000 Hz, pitch above about 400 Hz) and `low` (voiced 100 to 350 Hz, pitch below about 350 Hz);
  - `f0`, `level`, `beat_t`, `down_t` (bar starts) and `tempo`.
- `tools/s11_full2/s11_music_fx.py` reads them with `fx(name, t)` and wrappers (`fx_bass`, `fx_kick`, `fx_timp`, `fx_strings`, `fx_swell`, `fx_brass`, `fx_choir`, `fx_high`, `fx_low`, `fx_pulse`, `timp_hits`). If the file is missing every effect returns 0, so the film still renders.
- In the core module `s11_full2.py`:
  - `loud(t)` (smoothed, percentile-normalised `rms`) and `BEATS` (from `beat_t`) come from `features.npz`;
  - `beat_pulse(t)`, `hit_pulse(t, times)` and `intensity(t)` (19 section levels mixed with loudness) drive camera speed (`cam_speed`, `music_pace`), shake on slams (`cam_shake`) and a lens punch (`fov_punch`);
  - hand-measured constants: `SLAM1..3` (82.08, 162.86, 201.73), `DROP1..3` (75.2, 156.0, 197.2), `CODA` 199.62, `LAST_CHORD` 254.07, the `HIT` dict of 26 named cue times, and later `KEY_MOMENTS`.
- Neither the recording nor the `.npz` files are in git. The render machines received the two `.npz` files as private assets on the review page, as base64 text, and checked their SHA-256 before use.

## 4. How the film is built: a map of the code

### In plain words
The film is about 18,000 lines of Python in `tools/s11_full2/`. One core file holds the timeline, the camera, the music helpers and shared tools. Each scene has its own file, owned by one builder. All of them describe the same world, and the renderer asks each one, for every frame, "what do you look like at this moment?"

### The core: `s11_full2.py` (about 1,660 lines)
- **The timeline (`EDIT`).** 70 blocks, each a start time, an owner (church, stage, zion, procession, coda, dance, core) and a note. The blocks run from the intro's church shots, through the Earth, Verse 1 on Zion, slam 1 on the stage, the conductor, the Verse 2 march, Chorus 2, the coda's sunrise and sky orchestra, to the last chord and the end card. Every block has exactly one camera shot.
- **The camera (`SHOTS`).** Each scene file exports its shots. The core collects them in time order, turns each into a camera move, and paces the move by the music. The camera goes faster where the music is strong, shakes on slams and punches in on hits.
- **Places.** All in metres:
  - Mount Zion's foot at (0, 0, -420), with seven terraces up to a 70 m summit;
  - the church of light on the summit, with the orchestra's square in front of it;
  - the Earth as a 46 m globe;
  - the coda's sky stage high above.
- **Music helpers.** `loud`, `beat_pulse`, `hit_pulse`, `intensity`, `cam_speed`, `music_pace`, `cam_shake`, `fov_punch`, the slams and the 26 named hits.
- **Phrases (`PHRASE_LIST`).** 18 entries, each with one or two lines, four times (arrive, readable, read end, gone), a strong flag, a style (light, people, blaze or fly) and an exit. Helpers like `keep_out_of_words(t, pos)` let any scene fade its points where a phrase sits on screen.
- **Shared tools:**
  - `Comet`: a head, a tapering trail, glow and sparks, brightened on beats and hits.
  - `CloudBank`: Gaussian puffs under a cloud-shaped envelope.
  - `Pillars`: vertical columns of light with a pool on the sea.
  - `add_light` and `add_rays`.
  - The night-to-day Earth: the globe in navy and emerald, a dawn circle spreading from Korea, city lights that switch on beat by beat outward from Korea, and nine curved rivers of people flowing to Korea.
- **The light budget** (Phase K) and the shot-by-shot exposure.

### How a building becomes light
**In plain words.** Each real church was modelled by hand from the photo on its official dedication post. It was not traced or scanned: it was described as a short list of simple shapes, the way an architect would sketch it. For example: a main block, a tower, a pitched roof, a row of arched windows, a band of glass, a canopy over the entrance. The program then draws each shape's edges as lines of light, puts a warm point in every window, and places the building on its plot facing Zion. This is why the churches read as elegant line drawings rather than solid buildings, and it is where more detail would most improve them.

**Technical detail.**
- Each catalogue entry has id, name, city, country, source (the post's URL), year, size and parts.
- The part kinds are box, cyl, gable, hip, dome, spire, windows, arch_windows, glass_band, fin_row, canopy, disc, cross and steps.
- The 226 buildings have 1,091 parts: box 496, windows 144, glass_band 131, gable 66, canopy 60, fin_row 49, arch_windows 43, cyl 41, hip 27, steps 20, spire 7, dome 4, disc 3.
- A `_Pen` samples points along each edge, giving every point a role: edge (pearl outline), glass (blue grid), window (warm) or accent.
- Placement (`_layout`): Korean churches go on the plots (the summit's smallest first, then the terraces front-first, then the sea rings), scaled to fit each plot. The rest go into rings at 430 to 3,050 m, kept clear of the march route, the rivers, the cameras and each other.
- Births come in 43 waves timed to the music and snapped to the beat, so the city grows with the song.
- Each church is two fixed point sets (outline and windows). Their brightness per frame comes from the light budget, an occlusion test against the terraces, the phrase guard and the music.

### How people are made
Bodies come from the engine (section 1): a mesh with motion capture, with no faces, drawn as points. Song 11 adds subclasses:
- `Choir`: sways every two beats;
- `Players`: a 4-beat playing loop locked to the measured beats;
- `WaveCrowd`: true figures acting raise and open gestures as each wave reaches them;
- far crowds: cheap "glitter people", drawn as points with two strokes of light for the arms.

- **Six builders** (cloud sessions), each owning specific files and its own branch. They received tasks ("TASK ZION: ..."), kept their own improvement lists, checked their work with stills, pushed, and reported "BUILT".
- **Seven render machines** (A to G), one per section, each re-rendering its section whenever the film code changed, uploading the result and reporting "SECTION DONE".
- **One reviewer**, which measured every new video second by second (brightness, colour, sync, glare, words crossed) and posted findings with suggestions.
- **The review page**, Anthony's dashboard: the newest video of each section, live progress, findings with Approve and Decline, and request boxes.

Before the cloud builders existed (until about 07:50 on 11-19), the same work was done by helper agents running inside the coordinator's own session, on its four cores: five scene threads in rounds 1 to 4, then specialists in rounds 5 to 7.

### Technical detail
- **Merging.** `live/merge_builders.sh` fetches, fast-forwards `backdrop2/s11-full`, merges every builder branch that is ahead, and pushes. Each builder owned different files, so merges never conflicted. After a merge the coordinator compiled every module and rendered a few stills in a fresh process before trusting it.
- **Render machines.** Set up from MACHINE-PROMPT.md:
  - system packages for software OpenGL and ffmpeg, and Python packages (numpy, scipy, librosa, moderngl, pillow, fonttools, soundfile, numba);
  - the fonts, the pinned engine;
  - the two music files from the page, checked by SHA-256, and its own section's audio clip.

  Then the loop:
  1. Fetch the branch. If the film code changed, render the section's 5-second pieces with four workers (`render_chunks.py`), writing progress to `fleet/<letter>` on the page.
  2. Join with `section_build.sh`, look at two frames, upload, and set the fleet doc to ready with the URL and `video_at`.
  3. Send one message to the coordinator.
- **The reviewer** (its own cloud session). It downloaded each new section, extracted frames, measured the mean brightness and colour strength every second, checked sync on known hits, and posted findings (title, time, detail, suggestion). It never edited code.
- **The page.** `live/review_page.html` with its `db` collections (Phase F above). It shows the newest machine video at once, the real upload time, a storage meter, the "Clear old files" button (it keeps the keep list, the newest videos and anything under 30 minutes old) and a hideable "Done and closed" list.
- **Finishing and stopping.**
  1. Builders push one last change and stop.
  2. The coordinator merges, checks stills from a cold cache, and sends `FINAL <X>`.
  3. Each machine renders once, marks its fleet doc FINAL, and stops.
  4. To stop at once: interrupt every session, then send `STOP <X>` so nothing in the background keeps rendering or uploading.

## 6. The problems, how each was found, and what each taught

Each entry gives the symptom, how it was traced, the fix, and the rule kept since.

1. **Washed-out brass moments (01:50).** Lowering the flashes changed nothing. Comparing stills with parts switched off showed the cause was the sun's rays and glare behind the church. The sky was deepened and the rays cut in those views. *Lesson: measure by switching parts off before changing anything.*
2. **Silent music reactions on new machines (03:13).** Machines without the recording rendered pieces where nothing reacted to the music. Fixed by preparing the audio on every machine before it renders. *Rule: a machine checks its music files by checksum first.*
3. **A machine's upload blocked by its own safety check (04:22).** Left for Anthony to approve. *Rule: never work around a safety or permission block.*
4. **Missing fonts in a frozen copy of the code (04:12).** Fixed with a link to the fonts.
5. **Pieces held back until a batch finished (05:33).** Uploading each piece at once was allowed but not required. It is now required.
6. **Picture half a second behind the sound (06:26).** Measured: the video track started 0.533 s late. The cause was skipping with `-ss` on the joined input. Fixed with exact trim filters (`4dac735`).
7. **Scrambled sections (06:58).** Two sections had identical brightness frame by frame. The cause was a shared list file read by parallel joins; it was the coordinator's own mistake. Fixed with a private list per join (`503d375`). *Rule: after any join, check that the right scenes appear at the right times and that a known hit's flash lands on its sound.*
8. **Drive refuses large uploads (06:41).** Session uploads above a few MB fail, and the old videos were 7 to 26 MB. Old versions are therefore not archived, and the page keeps only the newest.
9. **Page storage nearly full** (1.05 of 1.07 GB, later 888 MB of 1 GB). Fixed with the one-tap cleanup and the keep list.
10. **Picture 3 to 4 frames early on every hit (f20).** The measured hit times sit about 0.1 s before the audible attack. Every frame is now drawn 0.1 s later (`PICTURE_DELAY`).
11. **The end-card crash (07:56).** A fully transparent glow could not be cropped, and it blocked every render. *Rule: builders render stills in a brand-new process before every push.*
12. **The page showing an old video.** One machine replaced its progress record each render (losing the link) and wrote bad times. Machines now only update the record, write full UTC times and `video_at`, and the page always shows the newest video with its real upload time.
13. **"Allow" prompts stalling the team** (08:23 to 12:29; the reviewer for about four hours). A cloud session's permission mode is fixed when it is created. Some calls still need a person to tap Allow, and the coordinator cannot change that. *Lesson: check every thread's status regularly, and tell Anthony at once when one is waiting on him.*
14. **The emblem misunderstanding (13:23 to 13:43).** "Just have one prominently showing on the Main church" was read as "no emblems anywhere else". *Lesson: when a new instruction seems to undo an earlier one, ask which parts it replaces.*
15. **A dark box behind the words (13:36).** The old way of keeping words readable was a darker region. It was removed and replaced with a white core, a coloured glow and a letter-hugging edge.
16. **Milky Zion (14:04).** Switching sets off one by one ruled out the soft glows; the grade's pale skies were lifting every dark. Fixed with deep night skies.
17. **Too bright, too much of the time (the final note).** The film moved from "everything bright" to a shared light budget with key moments.
18. **Slam glare.** 35% of the frame went near white for about 0.9 s. The slam became a short warm burst, with the rockets trimmed and kept out of the words. At quarter size, slam 1's flat-white area fell from 9.4% to 2.9%.
19. **Corner titles dark (14:59).** Darker scenes exposed an old "day" palette in the overlay. Fixed in code (`e18616c`) but not rendered.
20. **Starting another round after "stopping point" (15:16).** Anthony had said to finish up; the coordinator ordered one more render for two fixes. Anthony stopped it. *Lesson: "come to a stopping point" means stop after the final pass, not one more.*
21. **A cut 0.14 s early at 1:14.56 (f42).** The automatic beat tracker is a little off there. Moving the cut alone broke a church shot keyed to the old time, so it needs one joint change by two builders. Still open.

## 8. What I would do differently, and how to raise the quality

### My own mistakes, as lessons
1. **The shared list file** that scrambled the sections. Anything run in parallel must use private temporary files.
2. **Over-reading an instruction** (the emblems). When a new instruction seems to cancel an earlier one, confirm the scope.
3. **Starting another round after "stopping point".** Stop means stop after the agreed final pass.
4. **Letting the page fall behind and missing messages typed there.** The page is Anthony's main window, so it should be read and updated first.
5. **Checking cold-start renders only after a crash.** Fresh-process checks belong before every merge, not after a failure.

### How to get better quality
1. **A real graphics card.** This is the biggest single step. It would make the 1080p, 60 fps master and denser, sharper scenes about 10 to 50 times faster. The current rules (no paid services, nothing on the Mac) mean this needs Anthony's choice of a free or approved GPU source.
2. **Judge at final size earlier.** Drafts at 960x540 hide fine detail such as letters, building edges and the emblem.
3. **Approve a few key frames before building.** Agree each section's colour, brightness and composition against the promo first; much of the last day went into fixing washes, white-outs and boxes after they appeared.
4. **Fewer, larger rounds.** Many builders changing shared light at once caused regressions. Freeze a round, review the whole film, then start the next.
5. **More detail where the eye lands.** Give the most-seen churches (the summit and front terraces) and the close figures more parts, using Anthony's own photos as references.
6. **A hand-made cue sheet** of exact hit times, made once per song, so sync never depends on the beat tracker.
7. **Brightness targets from day one.** Use the reviewer's second-by-second measurement as a target from the first pass, not only at the end.

## Appendix D. Words in plain language

| Word | Meaning |
|---|---|
| Frame | One still picture; the film has 30 or 60 per second |
| Render | Calculating the frames from the scene description |
| Point set | A group of glowing points (a person, a church, a comet) that the program draws |
| HDR light buffer | A picture that can hold light far brighter than white before it is rolled off |
| Bloom | Bright light glowing into its surroundings |
| Filmic curve (tone mapping) | Rolling very bright light off gently, as film does, instead of clipping it to flat white |
| Depth of field | Things away from the focus going soft and round |
| llvmpipe / software OpenGL | Drawing with the CPU because there is no graphics card |
| Chunk / part / piece | One 5-second slice of the film, rendered on its own |
| Section | One of the seven parts of the song (Intro to Ending), one per machine |
| Branch, merge, commit | Git terms: a line of work, combining lines of work, and a saved change |
| Pull request (PR) | A request to bring a branch's work into the main line, reviewed before it is merged |
| Cloud session / thread | A separate Claude Code session on its own cloud computer |
| Fleet doc | A machine's progress record on the review page |
| Key moment | One of the 14 moments where the film is allowed full light |
| Light budget | How much light the film may use at each moment: about half at rest, full on key moments |
